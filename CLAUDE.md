# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm start                  # ng serve, dev server at localhost:4200 (uses environment.ts + local Firebase Emulator Suite)
npm run emulators             # firebase emulators:start (Auth/Firestore/Storage/Functions) — run alongside `npm start`
npm run build               # production build -> dist/trovalim/browser
npm run watch                # build --watch --configuration development
npm test                   # karma/jasmine unit tests (Chrome launcher)
npm run deploy               # ng build --configuration production && firebase deploy --project prod (live)
npm run deploy:preview          # ng build --configuration production && deploy to a Firebase Hosting preview channel on prod (temp URL, expires in 7d)
```

**Single live Firebase project** (`geovana-trovalim-prod`, aliased as `prod`/`default` in `.firebaserc`), plus `legacy` → `ellen-cavalcanti` (old project, kept as a read-only backup after the 2026-08 migration — no longer deployed to). There used to be a second cloud project (`geovana-trovalim-dev`) for testing changes safely; that was replaced by the local **Firebase Emulator Suite** (`npm run emulators`, config in `firebase.json`'s `emulators` block) for day-to-day dev, and by **Hosting preview channels** (`npm run deploy:preview`) for sharing a live-URL preview before merging to prod. `deploy:preview` builds with **`--configuration production`** (same as `deploy`) on purpose: it used to build `--configuration development`, but that ships no Angular Service Worker (`provideServiceWorker` has `enabled: !isDevMode()`), so a browser that had once loaded a *production* build of the same channel URL was left with a stale `ngsw-worker.js` that no dev deploy could replace or clean up — the stale SW then served stale cached lazy chunks and silently broke navigation to some admin routes (a chunk request fell through to the SPA HTML fallback → `ChunkLoadError`). Building preview with the production config keeps `ngsw.json`/`ngsw-worker.js` current so the SW self-updates. A browser already stuck in that state needs one hard reload (or DevTools → Application → Service Workers → Unregister) to pick up the fix. Both `environment.ts` and `environment.prod.ts` now point at the same `geovana-trovalim-prod` Firebase config — `environment.ts` additionally sets `useEmulators: true`, which `firebase.providers.ts` only honors when running on `localhost`/`127.0.0.1`, so any deployed build (including preview channels) always talks to the real prod backend. **Important:** a preview-channel deploy is hosting-only isolation — Firestore/Storage/Functions behind it are the real prod data, since it's the same project. Don't use preview channels to test destructive or data-mutating changes; use the emulator for that. Hosting site is `trovalim` on the old legacy project; the current project serves on its default `*.web.app` domain (no custom domain configured yet). Deploy targets can be scoped:

```bash
firebase deploy --only hosting --project prod
firebase deploy --only firestore:rules --project prod
firebase deploy --only functions --project prod   # requires Blaze plan
```

Cloud Functions live in `functions/` as a **separate npm package** (own `package.json`, plain CommonJS, no build step) — run `npm install` inside `functions/` before deploying or editing. It uses `firebase-admin` + `firebase-functions` v2 (`onCall`).

There is no lint script configured. No test files exist beyond the default `app.spec.ts` scaffold.

## Architecture

Angular 20 standalone-components app (no NgModules) backed entirely by Firebase (Auth, Firestore, Storage, Cloud Functions). No custom backend server — all business logic is either client-side (guarded by Firestore Security Rules) or in the small set of Cloud Functions under `functions/` for operations that require the Admin SDK (currently: deleting a user from Firebase Authentication, since the client SDK can only delete the signed-in user).

Routes are gated em `src/app/core/guards.ts` por `staffGuard` (owner/manager), `portalGuard` (client) ou `mentoriaGuard` (mentorado); telas admin somam `staffTabGuard('<key>')`, que respeita o `hiddenTabs` da conta — a mesma chave usada em `ADMIN_TABS`, então esconder uma aba pra um manager também bloqueia a rota, não só o link.

### Data model (Firestore)

- `/users/{uid}` — `UserAccount`. Role, and for clients an optional `companyId` pointing at `/empresas/{id}`. A client account with no `companyId` is an "unlinked" account waiting to be attached to a company.
- `/empresas/{id}` — `Empresa` (a client company). Owns `branding` (name/color/logo) and a `storageLimitMb`/`storageUsageBytes` pair. Multiple `/users` accounts (collaborators) can share one `companyId`, all inheriting that company's branding/storage limits at runtime via `AuthService.withCompanyData$`.
- `/projects/{id}` — `Project`. `ownerId` points at an `Empresa` id (or is `null` if unassigned). Has `steps: TimelineStep[]` embedded (no per-step id — matched by array index, so reordering matters) and subcollections `messages/`, `files/`, `internal/notes` (internal notes are a separate doc specifically so client-side reads of the project doc never leak staff-only content). Also carries denormalized `lastMessageAt`/`unreadForStaff`, written by `ProjectsService.sendMessage` on every message (client message → `unreadForStaff: true`) and cleared by `markMessagesRead` when staff opens the project's Mensagens tab — this is what powers the Painel's "Mensagens Não Lidas" card and the admin nav bell, without subscribing to every project's `messages` subcollection just to compute a badge.
- `/propostas/{id}` — `Proposta`. Generated from the pricing calculator inside a Prospecção lead (`AdminProspeccaoComponent.generateProposta`), items/total are a **frozen snapshot** (never re-reads `settings/pricing` after creation) editable only while `status: 'rascunho'`. The doc id is also the bearer token for the public acceptance page at `/proposta/:id` (no auth) — see `firestore.rules` `/propostas/{propostaId}`: public `get` once `status != 'rascunho'`, public `update` restricted to `status`/`acceptedByName`/`acceptedByEmail`/`declineReason`/`respondedAt` and only from `status == 'enviada'`.
- `/settings/{platform|projectStatuses|storageConfig|storageUsage|pricing|services|notifications|openai}` — config global da plataforma. Nessa ordem: ~~cor de marca~~ (o doc `settings/platform` não é mais lido nem escrito desde 2026-08-29 — a tela "Cor da Plataforma" foi removida; a cor virou a constante `DEFAULT_PLATFORM_COLOR = '#5B0F16'` = `--wine`, e `PlatformSettingsService.get$()` só devolve ela); lista configurável de status de projeto (`ProjectStatusOption` agora com `color?` — cor da etiqueta; sem valor, cai na cor padrão da chave em `DEFAULT_STATUS_COLORS` / paleta por índice — ver `statusColorFor()`; Configurações tem seletor por status + "Restaurar cores padrão", e `app-status-badge` pinta a etiqueta inline); limites de tamanho por tipo de arquivo; contador corrido de uso de storage; ~~catálogo de preços~~ + ~~catálogo de serviços~~ (desde 2026-08-29 os dois viraram um doc só, `settings/catalog` — `CatalogItem[]` com `unit`/`baseValue` nullable = "só descrição"; `PricingSettingsService`/`ServiceCatalogSettingsService` são views derivadas dele via `CatalogSettingsService`, e enquanto `settings/catalog` não existir a service compõe a lista a partir de `settings/pricing`+`services` — migração transparente, o 1º "Salvar Catálogo" grava o doc novo); ~~chave VAPID do Push~~ (desde 2026-08-29 é a constante `environment.vapidPublicKey`, não mais o doc `settings/notifications` — a tela foi removida); ~~chave da OpenAI~~ (desde 2026-08-29 é o segredo `OPENAI_API_KEY` do Functions, não mais o doc `settings/openai` — a tela foi removida; `functions/index.js` lê `OPENAI_API_KEY.value()`). Os ids `notifications`/`openai` continuam listados por histórico mas nenhum código lê/escreve mais. **Atenção aos ids**: são esses, curtos — não `platformSettings`/`projectStatusSettings`/`storageSettings`, que é como o nome da *service* sugere.
- Demais coleções raiz, criadas pelas telas novas da branch: `tasks` (Kanban), `leads` (Prospecção), `vagas` + `candidates` (R&S), `mentorships` (PDI), `careerTracks` (Carreira), `assessmentTemplates` + `assessments` (Avaliações), `calendarEvents`, `planningGroups` + `planningItems` (Planejamento), `auditLogs` (LGPD — só escrita, ninguém edita nem apaga depois, nem o owner), `contactSubmissions` (formulário do site público).

Storage usage is maintained as an **incremental counter** (`increment()` on upload/delete in `ProjectsService.bumpUsage`), not computed on read — both a per-company counter (`empresas/{id}.storageUsageBytes`) and a global one (`settings/storageUsage`).

### Security model

`firestore.rules` mirrors the role/ownership logic that also exists in TypeScript (`isStaffRole`, `managerCanAccessProject`, etc.) — when changing access rules, both places need to agree. Key rules to know:
- Only `owner` can create/delete `/users` docs or change `role`/`projectAccess`; managers can otherwise edit accounts.
- A manager's `projectAccess` field (if set, non-null) restricts which projects they can read/write.
- A client can read/write a project's `messages`/`files` only if they own it (`ownerId` matches their `companyId`) and the project isn't `hidden`; they may only **delete** files where `uploadedByRole == 'client'` (i.e. their own uploads), never staff-uploaded files.
- Storage rules (`storage.rules`) are a separate file and must be kept consistent with the Firestore-side upload/size-limit logic in `StorageSettingsService`.

### Cross-cutting patterns

- **Firebase DI**: all Firebase SDK handles (`Auth`, `Firestore`, `Storage`, `Functions`) are provided as injection tokens in `src/app/core/firebase.providers.ts` via `provideFirebase()`, not imported ad hoc.
- **RxJS↔Signals**: components read Firestore data via `*.service.ts` observables (thin wrappers in `firestore-rx.ts` around `onSnapshot`), converted to signals with `toSignal(...)` at the component level; mutations are plain `async` methods that call the service directly (no NgRx/store).
- **Best-effort Cloud Function calls**: client code that depends on a Cloud Function (e.g. `AccountsService.deleteAccount` calling `deleteAccountAuth`) treats the function call as best-effort — Firestore state changes proceed even if the function call fails, since Cloud Functions may not be deployed/billable in every environment. Follow this pattern for new Cloud Functions rather than making the client hard-depend on them.
- **Branding propagation**: a company's `branding` (color/logo) is looked up live and threaded through to whatever it's displayed on (project header, portal, message bubbles) rather than duplicated — see `AuthService.withCompanyData$` and the `ownerAccount`/`empresa` signals in the admin project/client components.
- **Company/project deletion cascades**: deleting an `Empresa` or a `Project` is destructive and cascades (deletes Storage files, subcollections, etc.) — see `ProjectsService.deleteProject` and the delete flow in `admin-client.component.ts`, which lets the operator choose per-linked-item whether to delete or just unlink before removing the parent.

## Design system (`src/styles.css`)

O visual segue o **Guia de Identidade Visual Web da TROVALIM** (dark luxury / editorial: burgundy + dourado, tipografia serifada em caixa alta, ícones outline, muito espaço negativo, bordas delicadas). O guia em si não está versionado no repo — o usuário tem o `.md` original.

**Regra número um: nada de cor literal fora do bloco de tokens no topo de `src/styles.css`.** Se precisar de um tom novo, ele vira token. Um hex solto num `style="..."` de template quebra silenciosamente um dos dois temas.

### Duas camadas de tokens

1. **Marca / navegação — fixas nos dois temas.** `--wine*`, `--gold*`, `--cream*` e os `--sidebar-*`. A sidebar, a barra do topo do portal e a tela de login são **sempre escuras**, por decisão de identidade: são a âncora da marca e não acompanham o tema. Componentes que vivem dentro da navegação (ex: o menu do sino, `.pnav-bell-menu`) precisam usar os `--sidebar-*` e não os de conteúdo — senão viram uma caixa branca colada no rodapé burgundy no tema claro.
2. **Conteúdo — trocam com o tema.** `--bg`, `--surface`, `--surface-2` (poços/linhas/cabeçalhos dentro de um painel), `--surface-3` (campos de formulário), `--heading`, `--graphite` (texto corrente), `--muted`, `--border{,-soft,-strong}`, `--track`, `--hover`, `--accent-text`, `--accent-soft`, `--danger*`, `--success*`, `--role-*`, `--scrim`, `--shadow-*`. Definidos em `:root` (tema claro, que é o padrão) e sobrescritos em `:root[data-theme='dark']`.

**`--gold` vs `--accent-text`**: `--gold` (`#C9A06A`) não tem contraste como texto sobre branco. Ele serve pra preenchimentos, traços, bordas e ícones — que funcionam nos dois temas. Texto com cara de dourado usa `--accent-text`, que é um bronze escuro no claro e o próprio dourado no escuro.

### Tema claro/escuro

`ThemeService` (`core/theme.service.ts`) escreve `data-theme` no `<html>` e guarda a escolha em **dois lugares**: `localStorage['trovalim.theme']` (cache por navegador, lido antes do 1º paint pelo script inline do `index.html` — sem flash) e, quando há sessão, no campo `themePref` do doc `/users/{uid}`. Ao logar, `App` chama `theme.applyFromAccount(userData.themePref)` e o valor da conta vence o cache local — é o que faz a preferência seguir a pessoa entre dispositivos (num navegador virgem há um flash claro→escuro no 1º login, inevitável: o script inline não conhece a conta ainda). `set()` persiste nos dois; `applyFromAccount()` só alinha sessão+cache (não reescreve no Firestore). UI em Configurações → Aparência (`.segmented`). Regra: `firestore.rules` `/users/{userId}` ganhou uma cláusula que deixa **qualquer conta** gravar só `themePref` no próprio doc (`diff().affectedKeys().hasOnly(['themePref'])`) — precisa de `firebase deploy --only firestore:rules` ao promover; até lá o toggle já funciona pra staff (a cláusula `isStaff()` existente cobre).

Um script inline no `<head>` do `index.html` aplica o `data-theme` **antes do primeiro paint**; sem ele a página nasce clara e pisca pro escuro quando o Angular sobe. Ele repete a lógica do serviço de propósito — se mudar a chave ou o default num, mude no outro.

### Tipografia

Títulos em **Cinzel**, corpo em **Montserrat** (Google Fonts, carregadas no `index.html`). O guia pede Trajan Pro nos títulos, mas é fonte paga da Adobe e não existe no Google Fonts — Cinzel é o substituto mais próximo (mesma origem em capitais romanas). Se um dia houver licença do Trajan, é trocar o `@font-face`/link e o `--serif`. Títulos nunca em bold: peso 400, caixa alta, bastante `letter-spacing`.

### Navegação (`PnavComponent`)

O mesmo componente é sidebar no admin e barra no topo fora dele — o que decide é `visibleTabs.length > 0` (só o admin passa `[tabs]`). Ver a nota sobre `@HostBinding('class.pnav-sidebar-host')` na seção de pendências abaixo.

- Sidebar de **300px** (guia), gradiente vertical discreto, item de 52px com ícone outline + label, ativo com preenchimento `--wine` e barra dourada à esquerda.
- **A sidebar não rola inteira**: só `.pnav-tabs` rola (`flex:1; min-height:0; overflow-y:auto`), então marca no topo e perfil no rodapé ficam sempre à vista. Sem eyebrow/tagline no lockup da sidebar (2026-08-30) pra ganhar altura. Cada `.pnav-tab` é `flex:1 1 auto` com `min-height:38px`/`max-height:56px`: quando tudo cabe as abas **crescem pra preencher a coluna toda** (sem vão no rodapé); quando não cabe (viewport baixa) elas ficam no piso de 38px e `overflow-y:auto` entra como rede de segurança. Cabe sem rolagem de ~820px de viewport pra cima. No estado recolhido (rail 76px) o `.pnav-logo` tem `padding-top:3rem` pra não ficar sob o `.pnav-collapse-btn` (que é `position:absolute` no topo).
- **Ícones vêm de `ADMIN_TABS`** como `icon?: string[]` — uma lista de `d` de `<path>` num viewBox 24x24, traço 1.8px. É dado puro pra `ADMIN_TABS` continuar sendo uma única lista declarativa, em vez de um componente por ícone. O guia pede um único estilo de ícone (outline/Lucide) em toda a plataforma — não misturar com preenchidos.
- O `PnavComponent` lê o papel da conta do próprio `AuthService` (não como `@Input`) pra montar o card de perfil, justamente pra não obrigar as 17 telas admin a passarem mais um atributo.

### Armadilhas já pagas aqui

- **Nunca use `background-attachment: fixed`.** O brilho radial do fundo usava isso e o navegador reprocessava o gradiente inteiro a cada quadro de scroll — repaint caro o bastante pra travar a renderização de páginas longas de forma reproduzível (screenshots do preview passaram a dar timeout). O fundo hoje é uma camada `body::before` com `position: fixed`, que a GPU compõe em vez de repintar.
- **`.card` com `padding:0` + tabela precisa que o filho herde o raio.** As telas de listagem (Projetos, Contas, Empresas) põem a `<table>` num `.card` de `padding:0`. O fundo do `<thead>` é um retângulo e aparecia por baixo dos dois cantos arredondados do topo do card. Resolvido com `border-radius: inherit` em `.data-table-wrap` (o `overflow-x:auto` dele já criava o contexto de recorte). Qualquer bloco novo colado na borda de um card com `padding:0` tem o mesmo problema.

## Known issues / pitfalls

- **`AccountsService.createAccount()` leaks into real prod Auth even when testing against the emulator.** It opens a *secondary* Firebase app (`initializeApp(environment.firebase, 'Secondary-...')`) so creating a new account doesn't swap out the admin's own session — but that secondary app's `Auth` instance is built with a bare `getAuth(secondaryApp)` and never gets `connectAuthEmulator(...)` called on it, unlike the primary app's `FIREBASE_AUTH` token in `firebase.providers.ts`. Net effect: clicking "Nova Conta" while running `npm start` + `npm run emulators` creates the Firestore `/users` doc in the emulator (fine), but calls `createUserWithEmailAndPassword` against the **real** `geovana-trovalim-prod` Authentication — a real login gets created in production every time this is tested locally.
  - Confirmed while testing on 2026-08-25: created a `mentorado@trovalim.local` test account through the UI against the emulator, and it could not be found when logging into the emulator afterward — consistent with the account having actually landed in real Auth instead.
  - **Action needed, not yet done**: check the [Firebase Console → Authentication](https://console.firebase.google.com/project/geovana-trovalim-prod/authentication/users) for stray test accounts (at minimum `mentorado@trovalim.local`) and delete them by hand.
  - **Fix, not yet applied**: the secondary app's `Auth` instance needs the same `shouldUseEmulators()` / `connectAuthEmulator(...)` treatment as the primary one in `firebase.providers.ts` — pull that emulator-detection logic into a small shared helper both call.
  - This same secondary-app pattern is also used for anything else in `accounts.service.ts` that spins up a throwaway Firebase app — audit for the same gap before relying on emulator isolation for those paths too.

- **`npm install` needs `--legacy-peer-deps`.** `@angular/service-worker@20.3.29` (added for PWA support) pins an exact peer on `@angular/core@20.3.29`, while the rest of the `@angular/*` packages resolve to `20.3.27` — a real, harmless patch-version skew, but npm's default resolver refuses to install over it (ERESOLVE loop). Run `npm install --legacy-peer-deps` instead of a bare `npm install` until the `@angular/*` versions catch up to each other.

- **`computer{action:"left_click", ref:...}` can silently no-op on this app's buttons in the sandboxed preview browser**, even with a fresh `read_page` ref and correct coordinates (no error thrown, click just doesn't reach the Angular handler — confirmed 2026-08-25 clicking "Excluir dado" in `/admin/lgpd` twice with no effect). Dispatching a real DOM click via `javascript_tool` (`document.querySelectorAll('button')` → find by text → `.click()`) worked reliably every time in the same session. When a `computer` click on this app seems to do nothing, don't assume the app is broken — retry with a scripted `.click()` before concluding there's a bug.

- **Service Worker registration can't be verified from a sandboxed preview/proxy browser.** `fetch('/ngsw-worker.js')` succeeds (200, correct MIME) but `navigator.serviceWorker.register(...)` itself fails with a generic `TypeError: ... An unknown error occurred when fetching the script` when the app is opened through an embedded/proxied preview browser (observed 2026-08-25 testing PWA support via a local static server through Claude Code's Browser pane). This reproduces even registering the exact same URL that `fetch` just proved reachable, so it's a limitation of that browser sandbox's networking (SW registration uses a different network path than page `fetch`), not an app bug. Verify PWA installability/offline behavior in a real browser tab (or `ng serve`'s production-equivalent build served normally) instead of relying on an embedded preview for this specific check.
